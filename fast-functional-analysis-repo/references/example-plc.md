# 작성 예시 — PLC 통합관리 솔루션 (발췌)

실제 분석에서 가져온 발췌다. 전체를 옮기지 않고 **판단이 드러나는 부분**만 실었다. 분량이 아니라 이 정도의 구체성과 솔직함이 기준이다.

---

## 1. 기본기능 재정의 — 이 분석의 전환점

**Rev 0.1**
> 설비 이상을 조기에 감지하고 담당자에게 알린다

경쟁자 테스트 실패. 모든 설비 모니터링 제품이 이 문장을 만족한다. 이 기본기능으로는 "왜 우리 제품이어야 하는가"에 답할 수 없고, 실제로 Rev 0.1의 기능 트리는 범용 알림 시스템과 구분되지 않았다.

**Rev 0.2**
> 1차 대응자(오퍼레이터)가 스스로 처리할 수 있는 범위를 최대화하고,
> 그 범위를 넘는 문제는 전문가에게 **준비된 상태로** 인계한다

*"준비된 상태"란 — 전문가가 도착했을 때 ① 무슨 일이 있었고 ② 오퍼레이터가 무엇을 시도했으며 ③ 현재 어떤 상태인지가 이미 정리되어 있음을 뜻한다.*

모호한 용어를 즉시 정의한 것에 주목. 이 정의가 없으면 "인계한다"가 단순 알림으로 축소 해석된다. 정의를 붙이는 순간 그것을 담당할 기능(F4.2 도착 전 상황을 전달한다)이 필연적으로 생긴다.

**이 재정의가 트리 전체를 바꿨다**: F3·F4가 "조치 안내"·"상황 전파"에서 "Tier-1 자율처리"·"Tier-2 전문가 지원"으로 재편, "대응 주체를 판별한다"는 기능 신설, 세부기능 34 → 41개, 제품 무게중심이 검출에서 대응으로 이동.

## 2. 설계 제약

```js
constraints: [
  "<b>AI는 제어하지 않는다</b> — 시스템은 PLC에 대해 <u>읽기 전용</u>이며, 조작은 반드시 사람이 수행한다. AI의 출력은 '지시'가 아니라 '안내'다. (2-Tier 모델을 채택하는 순간 가장 중요해지는 제약)",
  "<b>PLC 무변경 원칙</b> — 기존 PLC 프로그램·스캔타임에 영향을 주지 않는 읽기전용/패시브 취득만 허용.",
  "<b>브랜드 독립성</b> — 미쓰비시·지멘스·로크웰·오므론·LS ELECTRIC 혼재 환경에서 동일 UX.",
  "<b>OT 보안</b> — IEC 62443 기준 망분리·읽기전용 계정."

```

각 제약이 **왜 이 제품에서 특히 중요한지**까지 적혀 있다. "보안이 중요하다" 수준으로 쓰면 QFD 지붕에서 쓸 수 없다.

```js
{id:"F3", sh:"Tier-1", name:"오퍼레이터가 스스로 조치하게 한다",
 en:"Tier-1 Operator Self-Service",
```

```js
 5,5,5,"시험","Attractive",1,1],

["F3.4","조치 가능 범위를 경계짓는다",

["F3.7","조치 결과를 검증한다",
```

기능명이 전부 동사+명사 종결형이고, 적용기술 열에 **정책까지** 들어가 있다("미확인 시 '모른다' 응답 정책"). 정책은 기술만큼이나 구현 항목이다.

세세부기능으로 내려가면:

```js
["F3.2","F3.2.1","온디바이스 sLLM + RAG 파이프라인 구축"],
["F3.2","F3.2.2","실시간 태그값 Tool-calling 연동"],
["F3.2","F3.2.3","음성 입출력(STT·TTS) 핸즈프리 구현"],
["F3.2","F3.2.4","근거 출처 인용 강제 + '모른다' 응답 정책"]
```

적용기술 나열이 그대로 실행 태스크가 되었다. 이 계층이 있으면 기획 문서가 곧 개발 백로그다.

## 4. 흐름도의 분기점과 복귀점

```js
{sid:"F2.7 · 분기점", kind:"gate",
 text:"<b>대응 주체를 판별한다</b>",
 note:"L0 안전정지 / L1 자율 / L2 원격지원 / L3 전문가"}

{sid:"F3.7 · 복귀점", kind:"gate",
 text:"<b>조치 결과를 검증한다</b>",
 note:"신호로 정상복귀 확인 → 성공: 종료·기록 / 실패: 에스컬레이션"}
```

흐름 도입부에 이렇게 적었다:

> 이 흐름도가 곧 제품의 정의다. 기능분석의 모든 항목은 이 흐름 위의 어느 한 지점을 담당한다. 특히 **분기점(F2.7)**과 **복귀점(F3.7)**이 이 모델의 성패를 가른다.

학습 루프:

> **학습 루프 (F5)** — Tier-2에서 해결된 사례는 조치 절차로 정형화되어 다음번 동일 이벤트에서 **Tier-1 안내로 강등**된다. 즉 시간이 지날수록 오퍼레이터가 처리할 수 있는 범위가 넓어진다. 이 루프가 작동하지 않으면 본 솔루션은 단순 알림 시스템으로 퇴화한다.

마지막 문장이 핵심이다. **작동하지 않으면 무엇이 되는지**까지 적었다.

## 5. 최대 리스크 callout

```js
callout: {
  title: "이 모델의 최대 리스크 — 판별 오류",
  body: "F2.7이 <b>L3를 L1으로 잘못 분류</b>하면 오퍼레이터가 감당 못할 일을 시도하게 되어 설비 손상·안전사고로 이어진다. 반대로 <b>L1을 L3로 과분류</b>하면 전문가 호출이 줄지 않아 솔루션의 존재 이유가 사라진다. 따라서 초기에는 <b>안전측 편향(L3 과분류 허용)</b>으로 시작해 실적 데이터로 점진 완화하는 설계가 타당하다. 이 비대칭 오류비용은 Kano 설문이 아니라 <b>FMEA로 다뤄야 할 항목</b>이다."
}
```

오류의 두 방향을 각각 쓰고, 대가가 다르다는 것을 밝히고, 그래서 어떤 초기 설정이 타당한지까지 이어졌다. 마지막에 **이 문제는 Kano/QFD로 못 다룬다**는 방법론적 한계까지 명시했다.

## 6. 포트폴리오 해설

```js
portfolioNote: "<b>주목</b> — 2-Tier 모델의 심장인 <b>F3.2(자연어 QA)·F3.3(단계별 확인)·F4.3(래더 추적)·F4.5(원인 순위화)</b>가 모두 우상단 <b>전략과제</b> 영역에 몰려 있다. 즉 이 제품의 차별화는 전부 고난도 영역에 있고, 좌상단 Quick Win만 구현하면 <u>Rev 0.1의 단순 알림 시스템으로 회귀</u>한다. Phase 1에서 F3.2의 최소 기능(웹 기반 QA)을 반드시 검증해야 하는 이유다."
```

분포를 서술하지 않고 **다음 행동을 바꾸는 판단**을 썼다. 어떤 기능이 어디 있는지 → 그래서 무슨 함정이 있는지 → 그래서 Phase 1에 무엇을 넣어야 하는지.

## 7. KPI — 베이스라인을 비워둔다

```js
rows:[
  {label:"현행 (베이스라인)", note:"실측 필요", v:null, placeholder:"측정되지 않음 — Phase 1 첫 과업"},
  {label:"Phase 1 목표", note:"L1 유형 한정", v:35},
  {label:"Phase 2 목표", note:"검증루프 가동", v:55},
  {label:"Phase 3 목표", note:"지식 강등 누적", v:70}
]
```

> **정의** — 발생 이벤트 중 오퍼레이터가 전문가 호출 없이 종결한 비율.
> **주의** — 위 목표치는 설계 가설이며, 현행 베이스라인 실측이 Phase 1의 첫 번째 과업이다. 베이스라인 없이 이 지표를 제안서에 쓰면 검증 불가능한 약속이 된다.
> 함께 볼 보조지표: 전문가 호출 건수, MTTR, L1 판별 정확도, **오퍼레이터 조치 후 재발률**.

마지막 보조지표가 중요하다. 재발률이 없으면 "대충 넘기고 종결 처리"가 KPI 최적 전략이 된다.

## 8. VOC — 날것의 말

```js
["V01","오퍼레이터","알람이 떠도 뭘 해야 할지 몰라 결국 반장을 부른다","조치 방법이 즉시 제시될 것","F3.1, F3.2"],
["V03","오퍼레이터","손에 장갑 끼고 기름 묻은 채로 화면 못 만진다","말로 묻고 들을 수 있을 것","F3.2 (음성)"],
["V05","오퍼레이터","야간·주말에는 물어볼 사람이 아예 없다","사람 없이도 물어볼 데가 있을 것","F3.2, F6.2"],
["V08","설비담당자","밤에 불려 나가 보면 별것 아닌 일이다","정말 필요할 때만 호출될 것","F2.7, F3.4"],
["V15","안전·IT","AI가 시키는 대로 했다가 사고 나면 누가 책임지나","위험한 조치는 아예 제시하지 않을 것","F3.4, F3.5"]
```

V03을 "사용성이 중요하다"로 번역했다면 **음성 입력**이라는 해법이 보이지 않는다. V08은 설비담당자의 불만이 곧 F2.7(판별) 기능의 존재 이유임을 보여준다 — VOC와 기능의 연결이 억지가 아니라 자연스럽다.

## 9. Kano 계층 분리 경고

> 2-Tier 모델 채택으로 **응답자 계층 분리가 필수**가 되었다. 오퍼레이터와 PLC 관리자는 같은 기능에 대해 정반대 Kano 분류를 낼 수 있다 — 예: F3.4(가드레일)는 관리자에게 Must-be지만 숙련 오퍼레이터에게는 Reverse(있으면 불만)로 나올 수 있다.

> **Reverse 항목을 반드시 열어둘 것** — F3.4(조치 범위 제한), F3.3(한 단계씩 확인), F3.7(결과 검증 강제)은 숙련 오퍼레이터에게 <u>간섭</u>으로 인식될 수 있다. Reverse가 유의하게 나오면 '숙련자 모드 스킵' 설계가 필요하다.

구체적인 기능 ID를 지목해서 경고했다. "계층별로 다를 수 있다"는 일반론은 아무 지시도 하지 않는다.
