## 1. 기능 기술 규칙

### 동사 + 명사 + 종결형

가치공학(Value Engineering, L.D. Miles)의 원칙이다. 기능은 항상 **"~을 ~한다"**로 쓴다.

명사구로 쓰면 해법이 고정된다. "알림 시스템"이라고 적는 순간, 알림이 아닌 방식으로 같은 목적을 이루는 설계는 검토 대상에서 사라진다. 동사형 "이상을 알린다"는 목적만 남기므로 푸시·화면·음성·자동조치 등이 모두 후보로 살아 있다.

### 추상도를 계층에 맞춘다

같은 일도 계층에 따라 다르게 쓴다.

| 계층 | 기술 예 |
|---|---|
| 기본기능 | 오퍼레이터가 스스로 처리할 범위를 최대화한다 |
| 핵심기능 | 오퍼레이터가 스스로 조치하게 한다 |
| 세부기능 | 자연어로 묻고 답한다 |
| 세세부기능 | 온디바이스 sLLM + RAG 파이프라인 구축 |

세세부기능만 구현 태스크라서 기술명이 들어가도 된다. 3차까지는 **수단이 아니라 목적**으로 쓴다.

### 자주 나오는 나쁜 기술과 교정

| 문제 | 나쁜 예 | 교정 |
|---|---|---|
| 모듈명 | 데이터 수집 모듈 | 신호를 수집한다 |
| 기술명 | AI 챗봇 기능 | 자연어로 묻고 답한다 |
| 형용사 뭉개기 | 효율적으로 관리한다 | 무엇을 어떻게 하는지 특정 — 정비주기를 산출한다 |
| 두 기능 합침 | 감지하고 통보한다 | 두 개로 분리 — 이상을 검출한다 / 담당자를 호출한다 |
| 수동태 | 데이터가 저장된다 | 시계열로 저장한다 |
| 목적 없는 동사 | 처리한다 / 관리한다 / 지원한다 | 무엇을 어떻게 — "오탐을 억제한다" |

"관리한다", "지원한다", "처리한다"는 거의 항상 **아직 생각을 안 한 상태**의 신호다. 이 동사가 보이면 한 번 더 캐묻는다.

## 2. 기본기능 도출

### 절차

1. **현행 대안을 먼저 쓴다** — 이 제품이 없으면 고객은 지금 어떻게 하는가. 기본기능은 이 대안보다 나은 무언가여야 한다.
2. **고객이 돈을 내는 이유를 쓴다** — 기능 목록이 아니라 결과로.
3. **"그래서 뭐가 좋은데?"를 답이 안 나올 때까지 반복한다** — 더 못 올라가는 지점이 과업, 그 바로 아래가 기본기능.
4. **세 가지 테스트를 돌린다** (아래).
5. **문장 안 모호한 단어를 바로 정의한다.**

### 세 가지 테스트

**경쟁자 테스트** — 이 문장을 경쟁 제품도 만족시키는가?

> "설비 이상을 조기에 감지해 알린다" → 모든 모니터링 제품이 만족. 실패.
> "대응 주체를 전문가에서 현장 작업자로 내린다" → 통과.

기본기능은 카테고리 정의가 아니라 **이 제품의 정의**다.

**수단 테스트** — 구현 수단이 문장에 들어 있는가?

> "AI가 트러블슈팅을 안내한다" → "AI"가 수단. 실패.
> "작업자가 스스로 문제를 종결하게 한다" → 통과. AI든 매뉴얼이든 상관없이 목적이 살아 있다.

**"그래서?" 테스트** — 읽고 나서 "그래서 고객에게 뭐가 좋은가"가 남는가?

> "데이터를 체계화한다" → 그래서? 실패.
> "같은 고장을 두 번째부터는 현장에서 끝내게 한다" → 통과.

### 기본기능이 바뀌면 트리 전체를 다시 본다

기본기능 재정의는 국소 수정이 아니다. PLC 사례에서 "감지·통보"에서 "대응 주체 하향 이동"으로 바꾸자:

- 핵심기능 F3·F4가 "조치 안내"·"상황 전파"에서 "Tier-1 자율처리"·"Tier-2 전문가 지원"으로 재편
- 이전에 없던 세부기능 신설: 대응 주체를 판별한다 / 조치 결과를 검증한다 / 도착 전 상황을 전달한다
- 세부기능 34개 → 41개
- 제품 무게중심이 검출(F2)에서 대응(F3·F4)으로 이동 → 5.5 평가 매트릭스의 가치·차별성 최상위가 바뀜

**기본기능을 고쳤는데 하위 트리가 그대로라면 실제로는 안 고친 것이다.**

## 3. 계층 분해

### 핵심기능 묶는 기준

기능들을 묶을 때 기준은 "비슷해 보임"이 아니라 다음이다:

- **대상 사용자가 같은가** — 다르면 가른다
- **정보 밀도가 같은가** — 현장 작업자용 3줄 안내와 전문가용 래더 추적은 같은 기능이 아니다
- **허용 조작 범위가 같은가** — 권한이 다르면 가른다
- **실패했을 때 다음 경로가 같은가**

이것이 갈리는데도 한 핵심기능으로 묶으면, QFD 관계 매트릭스 한 칸에 상충하는 요구가 들어가 가중치가 무의미해진다.

### 세부기능의 입도

하나의 세부기능은 **하나의 요구품질(VOC 한 줄)에 대응**할 수 있어야 한다. 대응이 여러 개로 갈라지면 너무 큰 것이고, 여러 세부기능이 한 요구품질에 붙으면 너무 잘게 쪼갠 것이다.

25~50개가 실무 감각이다. 20개 미만이면 분해가 덜 됐고, 60개를 넘으면 3차와 4차가 섞였다.

### 세세부기능

3차의 "적용기술" 열에 나열한 기술 요소를 **실행 태스크 동사**로 바꾼 것. 각 3~4개.

| 세부기능 | 적용기술 | → 세세부기능 |
|---|---|---|
| 시계열로 저장한다 | TimescaleDB, Parquet 압축, 링버퍼 | 고속 링버퍼 샘플링 구현 / 시계열DB 스키마·보존정책 설계 / 계층적 다운샘플링·압축 저장 |

이 계층이 있으면 그대로 WBS·스프린트 백로그가 되므로, 기획 문서와 개발 계획 사이의 번역 비용이 사라진다. 개수가 3~4개를 크게 넘으면 3차가 너무 컸다는 신호다.

## 4. How-Why 검증

### 방법

트리를 완성한 뒤 인접한 두 계층씩 짚어가며 양방향으로 읽는다.

- **HOW (왼→오)**: "F3 오퍼레이터가 스스로 조치하게 한다 — **어떻게?**" → "자연어 QA + 단계별 확인 + 안전 가드레일 + 결과 검증"
- **WHY (오→왼)**: "F3.2 자연어로 묻고 답한다 — **왜?**" → "오퍼레이터가 혼자 끝내야 하니까"

양방향이 다 성립해야 연결이 옳다.

### 실패 패턴

**순환논리** — WHY로 올라갔더니 "그게 필요하니까"가 나온다.
→ 오른쪽에 하위기능이 아니라 구현 부품이 들어간 것이다. "벡터DB를 쓴다"는 기능이 아니라 수단이다.

**목차형 상위기능** — 왼쪽이 오른쪽들의 단순 합이다.
→ "F5 데이터 관리 = 저장 + 정리 + 백업"은 목차지 기능이 아니다. 상위기능은 하위기능들이 **함께 만들어내는 새로운 능력**이어야 한다. "F5 지식을 축적한다 — 조치 사례를 정형화해 Tier-1 처리범위를 넓힌다"처럼 하위의 합 이상이 나와야 한다.

**계층 건너뜀** — 핵심기능 바로 아래에 구현 태스크가 붙어 있다.
→ 중간 계층이 빠졌다. 3차를 채운다.

### 기록

검증 결과를 WHY / 기능 / HOW 3열 표로 남긴다(`LOGIC`). 과업부터 각 핵심기능까지 한 줄씩. 이 표는 나중에 "왜 이 기능이 있는가"를 묻는 사람에게 그대로 답이 된다.

## 5. 시나리오 흐름도

### 목적

기능 목록은 "무엇이 있는가"만 보여준다. 흐름도는 "언제 무엇이 작동하는가"를 보여준다. 이 흐름도가 제품의 정의가 되고, 기능분석의 모든 항목은 이 흐름 위 어딘가를 담당해야 한다.

**어느 단계에도 못 붙는 기능이 있으면** 그 기능의 정당성을 다시 검토한다. 대개 "있으면 좋을 것 같아서" 넣은 것이다.

### 반드시 찾아야 할 두 노드

**분기점(gate)** — 경로가 갈리는 판단 노드.
여기서 오분류가 나면 이후 전부가 틀어진다. 판단 기준을 표로 명시하고(등급 체계 등), 그 표가 **고객사와 합의해 확정할 산출물**임을 밝힌다. 판단 정확도가 곧 QFD 기술특성 목표치가 된다.

**복귀점(loop-back)** — 결과를 검증해 성공/실패를 판정하는 노드.
없으면 시스템은 "조치를 안내했다"까지만 하고 실제로 해결됐는지 모른다. 실패 시 어디로 가는지(에스컬레이션)까지 그린다.

이 둘은 거의 항상 **가장 위험하면서 가장 가치 있는** 기능이다. 리스크 절과 KPI 설계가 여기서 나온다.

### 학습 루프

시간이 지나면서 시스템이 좋아지는 경로가 있으면 흐름도 아래 별도로 적는다. 이 루프가 없으면 제품은 도입 시점 성능에 고정된다. 있는데 작동하지 않으면 무엇으로 퇴화하는지까지 적는다 — "이 루프가 작동하지 않으면 단순 알림 시스템으로 퇴화한다"처럼.

## 6. 기존 문서 개정(Rev-up)

이전 버전이 있으면 다음을 헤더와 본문에 남긴다.

- **무엇이 바뀌었는가** — 헤더 meta에 한 줄: "Rev 0.1 대비: 기본기능 재정의, 대응주체 판별 기능 신설, 세부기능 34 → 41"
- **신규 기능 표시** — `isNew: 1`을 붙이면 FAST 다이어그램과 표에 "신규" 배지가 붙고 필터가 생긴다. 개정 이유를 눈으로 추적할 수 있다
- **왜 바뀌었는가** — 해당 절 도입부에 근거를 쓴다. "두 모드는 대상 사용자·정보 밀도·허용 조작 범위가 완전히 다르므로 같은 기능으로 묶으면 QFD에서 상충하는 요구가 한 칸에 들어간다"

개정의 핵심은 **변경 사실이 아니라 변경 근거**다. 근거가 없으면 다음 개정 때 또 뒤집힌다.
