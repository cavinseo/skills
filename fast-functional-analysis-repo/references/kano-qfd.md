# Kano · QFD 연계 설계

FAST의 기능 트리는 "무엇을 만들 수 있는가"를 정리한다. Kano와 QFD는 "무엇을 만들어야 하는가"를 정한다. 이어붙이는 지점이 §4의 세부기능 목록이다.

---

## 1. VOC 수집

### 고객의 말 그대로 적는다

VOC는 **날것의 불평**이다. 이미 요구사항으로 번역된 문장은 VOC가 아니다.

| ✗ VOC가 아님 | ✓ VOC |
|---|---|
| 실시간 모니터링이 필요하다 | 설비가 멈춘 뒤에야 연락이 온다 |
| 사용성이 좋아야 한다 | 손에 장갑 끼고 기름 묻은 채로 화면 못 만진다 |
| 알람 정확도가 중요하다 | 알람이 하루에 수십 개라 이제 안 본다 |
| 지식관리가 필요하다 | 같은 고장이 반복되는데 기록이 사람 머릿속에 있다 |

번역된 문장은 정보를 잃는다. "사용성"이라고 쓰면 폰트 크기 얘기인지 장갑 얘기인지 알 수 없다. 날것으로 적으면 **음성 입력**이라는 해법이 바로 보인다.

### 요구 주체를 반드시 표기한다

각 VOC에 누가 한 말인지 붙인다. 같은 제품에 대해 계층마다 다른 것을 원하고, 이것이 QFD 가중치 분리의 근거가 된다.

계층 예: 현장 작업자 / 설비·보전 담당자 / 관리·구매 / 안전·IT

### 환산된 요구품질

VOC를 **긍정형 요구**로 바꾼다. "알람이 하루 수십 개라 안 본다" → "유효한 알람만 울릴 것". 이것이 QFD 좌측 축(WHATs)에 들어간다.

### 주 연관 기능

각 VOC에 대응하는 세부기능 ID를 적는다. **어느 기능에도 안 붙는 VOC가 있으면** 기능이 빠진 것이고, **어느 VOC에도 안 붙는 기능이 있으면** 그 기능의 정당성을 재검토한다. 이 교차 확인이 VOC 표의 실제 용도다.

## 2. Kano 모델

### 다섯 분류

| 분류 | 있을 때 | 없을 때 | 개발 함의 |
|---|---|---|---|
| **Must-be** 당연품질 | 만족도 안 오름 | 강한 불만 | 합격기준. 미충족 시 도입 무산 |
| **One-dimensional** 일원품질 | 만족 비례 상승 | 비례 불만 | 투자 대비 효과가 선형. 예산 조절 가능 |
| **Attractive** 매력품질 | 강한 만족 | 불만 없음 | 차별화의 원천 |
| **Indifferent** 무관심 | 반응 없음 | 반응 없음 | 개발 우선순위 최하 |
| **Reverse** 역품질 | **불만** | 만족 | 있으면 해가 된다 |

### 설문 형식

기능마다 긍정형·부정형 한 쌍을 묻는다.

- 긍정형: "이 기능이 **있다면** 어떻겠습니까?"
- 부정형: "이 기능이 **없다면** 어떻겠습니까?"

각각 5지선다: 마음에 든다 / 당연하다 / 아무렇지 않다 / 어쩔 수 없다 / 싫다.
두 응답의 조합을 Kano 평가표에 대입해 분류가 결정된다.

### Better / Worse 계수

- **Better = (A + O) / (A + O + M + I)** — 이 기능을 넣었을 때 만족이 올라가는 정도 (0~1)
- **Worse = −(O + M) / (A + O + M + I)** — 뺐을 때 불만이 커지는 정도 (−1~0)

Better가 높으면 차별화 카드, |Worse|가 높으면 필수 조건이다.
**이 계수로 §5.4 포트폴리오의 가치 축을 실측치로 교체한다.** 이것이 Kano 설문의 최종 산출물이다.

## 3. 응답자 계층 분리 — 사용자가 둘 이상이면 필수

같은 기능이 계층에 따라 **정반대로 분류될 수 있다.**

> 안전 가드레일(권한 밖 조치는 안내하지 않음)
> — 관리자·안전담당: **Must-be** (없으면 도입 불가)
> — 숙련 작업자: **Reverse** (내가 할 줄 아는 걸 막는다)

이 갈림은 설계 실패가 아니라 **정보**다. 두 계층의 분류가 갈리는 기능이 곧 **제품 내 모드 분리 설계의 근거**가 된다. 위 예시라면 "숙련자 모드에서 단계 스킵 허용, 단 안전 관련 항목은 예외" 같은 설계가 나온다.

계층별로 합쳐서 집계하면 이 정보가 통계적으로 상쇄되어 사라진다. **반드시 분리 집계하고, 갈리는 항목을 별도로 뽑아 본다.**

권장 표본: 주 사용자층 n≥30 (숙련도 상/하 분리), 전문가층 n≥20, 관리·구매 n≥10, 안전·IT n≥5.

---

## 4. Reverse 항목을 열어둔다

통제·확인·검증을 **강제**하는 기능은 숙련 사용자에게 간섭으로 느껴진다. 설문 설계 시 이런 기능들을 Reverse가 나올 수 있는 후보로 미리 표시하고 결과를 따로 본다.

Reverse 후보 유형:
- 단계별 확인을 강제하는 기능 (한 번에 한 단계씩)
- 조치 범위를 제한하는 기능 (권한 가드레일)
- 결과 검증을 강제하는 기능 (완료 처리 전 확인)
- 기록·보고를 의무화하는 기능

Reverse가 유의하게 나오면 기능을 없애는 게 아니라 **적용 조건을 설계한다** — 숙련도 기반 스킵, 옵트아웃, 안전 항목만 강제 등.

---

## 5. Must-be는 가중치가 아니라 합격기준

QFD 가중치 계산에 Must-be를 그냥 넣으면 안 된다. Must-be는 **점수를 매기는 항목이 아니라 통과/탈락을 가르는 항목**이다.

Must-be로 분류된 기능들을 별도 목록으로 뽑고 "미충족 시 도입 자체가 무산되는 기능"으로 명시한다. 이 목록이 곧 **최소 요구사양(MVP의 하한선)**이다.

가중치 경쟁은 One-dimensional과 Attractive 사이에서 벌인다.

## 6. QFD 품질의 집 축 구성

| 축 | 내용 |
|---|---|
| **좌측 (WHATs)** | 환산된 요구품질. 요구 주체 계층별로 가중치 분리 |
| **상단 (HOWs)** | §4 세부기능 또는 그 적용기술 |
| **관계 매트릭스** | ◎ 9 (강) / ○ 3 (중) / △ 1 (약) |
| **지붕 (상관)** | 기술특성 간 상충·시너지. **설계 제약에서 나온다** |
| **우측** | 경쟁 비교 — 경쟁 제품 / 대체 수단 / 무도입(현행) |
| **하단** | 기술특성 목표치 — 정량 수치로 |

### 2단계 전개를 권장

세부기능이 40개를 넘으면 HoQ 열이 40개가 되어 실무상 다루기 어렵다.

1. **1차 HoQ** — 상단 축을 **핵심기능(2차) 4~8개**로 놓고 돌린다. 어느 덩어리가 중요한지 결정
2. **2차 HoQ** — 1차에서 높게 나온 핵심기능만 골라 세부기능으로 전개

### 지붕(상충관계)은 제약에서 나온다

Phase 1에서 뽑은 설계 제약이 여기서 쓰인다. 상충은 대개 제약과 기능이 부딪히는 지점이다.

> 자연어 응답의 자유도 ↔ 안전 가드레일 (답변 범위 제한)
> 무침습 취득 ↔ 센서 증설 (물리 신호 보강)
> 망 분리 ↔ 모바일 푸시 알림
> 온디바이스 추론 ↔ 답변 품질 (모델 크기 제약)

상충을 찾지 못했다면 제약을 충분히 뽑지 않은 것이다. 상충 없는 설계는 없다.

### 기술특성 목표치는 흐름도의 분기점에서 나온다

하단 목표치는 임의로 정하는 게 아니라 §1 흐름도의 분기점·복귀점 성능에서 나온다.

> 분기점의 판단 정확도 ≥ 95%
> 자연어 응답 지연 < 5초
> 근거 인용률 100%
> 설치 소요 3일 이내

등급 체계 표를 만들었다면 그 표의 "목표 대응시간" 열이 그대로 목표치가 된다.

## 7. Kano·QFD로 다룰 수 없는 것

**오류비용의 비대칭은 Kano/QFD의 사각지대다.**

Kano는 "있으면 좋은가"를, QFD는 "얼마나 중요한가"를 다룬다. 둘 다 **틀렸을 때의 대가가 방향에 따라 다른 상황**을 표현하지 못한다.

> 판단 기능이 A를 B로 잘못 분류 → 안전사고
> B를 A로 잘못 분류 → 예전과 동일 (손해 없음)

이런 비대칭은 **FMEA(고장모드 영향분석)**로 별도로 다뤄야 한다. 분석 문서의 "다음 단계"에 FMEA 병행을 명시하고, 왜 Kano/QFD로 부족한지 이유를 적는다.

판단·분류·자동 결정을 하는 기능이 있으면 항상 이 점검을 한다.
