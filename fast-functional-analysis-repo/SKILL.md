# 기능분석 (FAST) 표준 절차

FAST는 "이 제품이 **무슨 기능을 하는가**"를 논리적으로 분해해, 무엇을 먼저 만들고 무엇을 버릴지 판단할 근거를 만드는 방법이다. 산출물은 인터랙티브 HTML 대시보드 한 장이다.

이 스킬의 가치는 템플릿을 채우는 데 있지 않다. **기능을 어떻게 기술하느냐가 이후 모든 판단을 좌우**하기 때문에, 분해 이전의 정의 단계에 대부분의 노력이 들어간다. 아래 워크플로는 그 순서를 강제한다.

## 산출물

`assets/template.html`을 복사해 상단 `DATA` 블록만 교체한다. 그 아래 `ENGINE` 영역(차트·표·필터·펼치기 렌더링)은 손대지 않는다. 차트 SVG, 라이트/다크 토글, 툴팁, 필터, 세세부기능 펼치기가 모두 데이터에서 자동 생성되므로 **분석에만 집중하면 된다**.

필드별 정확한 형식은 `references/data-contract.md`에 있다. 작성 후 반드시 `scripts/validate.py`를 돌린다.

## Phase 0 — 대상 파악과 질문

분석 대상이 무엇인지, 어떤 자료가 있는지 먼저 확인한다. 사용자가 기획서·제안서·요구사항 문서를 갖고 있으면 읽는다. 없으면 아래를 묻는다. 한 번에 다 묻지 말고 답을 못 할 것 같은 항목은 가설로 채운 뒤 "이건 가정입니다"라고 표시한다.

- 이 제품이 없으면 고객은 지금 **어떻게 그 일을 처리하고 있는가** (현행 대안)
- 고객이 실제로 **돈을 지불하는 이유**는 무엇인가
- 사용자 계층이 여럿인가 (있다면 각각 무엇을 원하는가 — 이게 갈리면 기능 설계가 갈린다)
- 절대 넘을 수 없는 제약은 무엇인가 (안전·법규·기존 시스템 무변경·예산)
- 시험/PoC 단계와 최종 상용 단계의 범위 차이

**대화나 첨부 문서에 이미 답이 있으면 다시 묻지 않는다.** 이전 Rev 문서가 있으면 그것을 출발점으로 삼고, 무엇이 바뀌었는지 헤더에 명시한다.

## Phase 1 — 과업과 기본기능 정의 (가장 중요)

여기서 잘못 잡으면 아래 전부가 틀어진다. 시간을 여기 쓴다.

### 과업(Task)
고객이 달성하려는 상태. 제품이 아니라 **고객의 목적**을 쓴다.
> "브랜드 혼재 설비의 비계획 정지 손실을 최소화한다"

### 기본기능(Basic Function)
제품이 존재하는 이유 한 문장. **이 한 문장을 찾는 것이 FAST의 핵심 작업이다.**

가장 흔한 실패는 기본기능에 **표면적 동작**을 쓰는 것이다. "이상을 감지한다", "데이터를 관리한다" 같은 문장은 거의 항상 틀렸다. 감지는 수단이지 고객이 사는 것이 아니다.

**검증 질문 세 가지 — 셋 다 통과해야 한다:**

1. **경쟁자 테스트** — 이 기본기능 문장을 경쟁 제품도 똑같이 만족시키는가? 그렇다면 아직 못 찾은 것이다. 기본기능은 차별화 지점을 품고 있어야 한다.
2. **수단 테스트** — 문장 안에 구현 수단(AI, 센서, 클라우드, 앱)이 들어가 있는가? 있다면 빼고 다시 쓴다. 수단은 3차 이하에서 다룬다.
3. **"그래서?" 테스트** — 문장을 읽고 "그래서 고객에게 뭐가 좋은데?"라는 질문이 남는가? 남으면 한 단계 더 올라간다.

**실제 사례 (PLC 통합관리 솔루션):**

| Rev | 기본기능 | 판정 |
|---|---|---|
| 0.1 | 설비 이상을 조기에 감지하고 담당자에게 알린다 | ✗ 경쟁자 테스트 실패 — 모든 모니터링 시스템이 이걸 한다 |
| 0.2 | 1차 대응자가 스스로 처리할 수 있는 범위를 최대화하고, 그 범위를 넘는 문제는 전문가에게 **준비된 상태로** 인계한다 | ✓ 대응 주체를 아래로 내린다는 차별화가 문장에 들어 있다 |

이 재정의 하나로 기능 트리 전체가 바뀌었다. F3·F4가 "조치 안내"·"상황 전파"에서 "Tier-1 자율처리"·"Tier-2 전문가 지원"으로 재편되었고, 이전에 없던 "대응 주체를 판별한다"는 기능이 신설되었다.

**기본기능에 모호한 말이 있으면 바로 아래에서 정의한다.** 위 사례의 "준비된 상태로"처럼. 정의하지 않으면 이후 모든 기능이 그 모호함 위에 쌓인다.

### 설계 제약(Constraint)
기능은 아니지만 모든 기능을 구속하는 조건. 제약은 기능 트리에 넣지 않고 별도로 세운다. 예: "AI는 제어하지 않는다 — 시스템은 읽기 전용이며 조작은 반드시 사람이 한다."

제약은 **기능이 아니면서 QFD 지붕(상충관계)의 원인이 되므로** 이 단계에서 빠짐없이 뽑아둔다.

## Phase 2 — 기능 분해

### 기능 기술 규칙: 동사 + 명사, 종결형

모든 기능은 **"~을 ~한다"** 형태로 쓴다. 명사구(모듈명)로 쓰면 안 된다.

| ✗ 이렇게 쓰지 않는다 | ✓ 이렇게 쓴다 |
|---|---|
| 데이터 수집 모듈 | 신호를 수집한다 |
| 알람 관리 기능 | 오탐을 억제한다 |
| AI 챗봇 | 자연어로 묻고 답한다 |
| 보고서 생성기 | 상황보고서를 자동 생성한다 |

**왜 중요한가** — 명사는 해법을 고정시킨다. "챗봇"이라고 적는 순간 챗봇이 아닌 해법은 검토 대상에서 사라진다. 동사형은 "자연어로 묻고 답한다"는 목적만 남기므로 음성·검색·가이드 UI 등 다른 수단이 살아 있다. 이것이 가치공학이 동사+명사를 고집하는 이유다.

### 계층

| 계층 | 개수 감각 | 성격 |
|---|---|---|
| 과업 | 1 | 고객의 목적 |
| 기본기능 (1차) | 1 | 제품의 존재 이유 |
| 핵심기능 (2차) | 4~8 | 기본기능을 달성하는 큰 덩어리. QFD 1차 HoQ의 축 |
| 세부기능 (3차) | 25~50 | Kano·QFD 분석 단위. 하나가 하나의 요구품질에 대응 |
| 세세부기능 (4차) | 각 3~4개 | 실행 태스크. 그대로 WBS·스프린트 백로그로 이관 |

핵심기능이 9개를 넘으면 묶임이 잘못된 것이다. 3개 이하면 너무 뭉쳤다.

**대상 사용자·정보 밀도·허용 조작 범위가 다르면 반드시 다른 핵심기능으로 가른다.** 같은 기능으로 묶으면 QFD에서 상충하는 요구가 한 칸에 들어가 가중치가 무의미해진다. (PLC 사례에서 Tier-1/Tier-2를 가른 이유가 이것이다.)

세세부기능은 3차의 "적용기술" 열에 나열한 기술 요소를 **실행 동사**로 바꾼 것이다. "TimescaleDB" → "시계열DB 스키마·보존정책 설계".

### How-Why 양방향 검증

FAST 다이어그램의 유일한 검증 장치다. 트리를 다 그린 후 반드시 수행한다.

- **왼쪽 → 오른쪽**: "이 기능을 **어떻게** 달성하는가?" → 오른쪽 하위기능들이 답이어야 한다
- **오른쪽 → 왼쪽**: "이 기능은 **왜** 필요한가?" → 왼쪽 상위기능이 답이어야 한다

한 방향만 성립하면 그 연결은 잘못이다. 흔한 오류:

- 오른쪽에 **하위기능이 아니라 구현 부품**이 들어가 있다 → 왜(WHY)로 거슬러 올라가면 "그게 필요하니까"라는 순환논리가 나온다
- 왼쪽 기능이 오른쪽 기능들의 **단순 합**이다 → 상위기능이 아니라 목차다. 상위기능은 하위기능들이 함께 만들어내는 **새로운 능력**이어야 한다

검증 결과는 대시보드 §2의 `LOGIC` 표에 WHY / 기능 / HOW 3열로 남긴다. 이 표가 곧 논리 감사 기록이다.

### 핵심 시나리오 흐름도

기능 목록만으로는 "언제 무엇이 작동하는가"가 안 보인다. 주요 사용 시나리오를 좌→우 흐름으로 그리고, 각 단계에 기능 ID를 붙인다. 이 흐름도가 **제품의 정의**가 된다 — 기능분석의 모든 항목은 이 흐름 위 어딘가를 담당해야 하고, 어디에도 못 붙는 기능은 정당성을 다시 검토한다.

흐름을 그릴 때 두 지점을 반드시 찾아 표시한다:

- **분기점(gate)** — 경로가 갈리는 판단 노드. 여기서 오분류가 나면 이후 전부가 틀어진다
- **복귀점(loop-back)** — 결과를 검증해 성공/실패를 판정하는 노드. 이게 없으면 시스템은 "했다고 주장"만 하고 끝난다

이 두 노드는 거의 항상 **가장 위험하면서 가장 가치 있는** 기능이다. 리스크 절과 KPI 설계가 여기서 나온다.

## Phase 3 — 정량화

세부기능마다 다음을 매긴다. 척도 정의와 판단 기준은 `references/quantification.md` 참조.

| 항목 | 척도 | 의미 |
|---|---|---|
| TRL | 1–9 | 기술성숙도. 1–3 개념, 4–6 시작품, 7–9 실환경 검증 |
| 난이도 | 1–5 | 구현 난이도 |
| 가치 | 1–5 | 고객 체감가치 — **엔지니어링 가설이며 Kano 설문으로 교체 대상** |
| 적용단계 | 시험 / 최종 | PoC 범위인가 상용 범위인가 |
| Kano 가설 | Must-be / One-dimensional / Attractive / Indifferent | 설문 전 가설 |
| Phase | 1,2,3 | 개발 단계 배치 |

### 추정치를 사실처럼 쓰지 않는다

이 단계 숫자는 전부 검증 전 추정이다. 대시보드 곳곳에 그렇게 적는다. 특히 대표 KPI를 다룰 때:

> **현행 베이스라인을 모르면 목표치는 검증 불가능한 약속이다.**

KPI 차트의 첫 행은 "현행(베이스라인) — 측정되지 않음"으로 두고(`v: null`), 베이스라인 실측을 다음 단계의 첫 과업으로 명시한다. 이것이 제안서의 신뢰도를 만든다. 숫자를 채워 넣는 것보다 **모른다고 정확히 말하는 것**이 강하다.

### 포트폴리오를 그리고 나서 **읽는다**

난이도 × 가치 산점도는 그리는 게 목적이 아니라 읽는 게 목적이다. 그린 다음 반드시 아래를 확인하고 그 결과를 `META.portfolioNote`에 적는다.

- **차별화 기능이 어느 사분면에 모여 있는가?** 우상단(고난도·고가치)에 몰려 있다면 → Quick Win만 골라 Phase 1을 짜면 제품이 평범해진다. 어떤 고난도 기능을 Phase 1에 반드시 넣어야 하는지 이름을 적시한다.
- **좌상단(저난도·고가치)이 비어 있는가?** 그렇다면 초기 성과를 보여줄 카드가 없다는 뜻이다.
- **우하단(고난도·저가치)에 뭔가 있는가?** 왜 하는지 정당화하거나 잘라낸다.

포트폴리오 해설이 "고르게 분포되어 있다" 수준이면 분석을 안 한 것이다.

## Phase 4 — Kano · QFD 연계

상세는 `references/kano-qfd.md`. 요점만:

**VOC는 고객이 실제로 한 말 그대로 적는다.** "실시간 모니터링이 필요하다"는 VOC가 아니라 이미 요구사항으로 번역된 문장이다. 진짜 VOC는 "알람이 떠도 뭘 해야 할지 몰라 결국 반장을 부른다" 같은 것이다. 날것의 불평이 훨씬 많은 정보를 담는다.

**사용자 계층이 둘 이상이면 Kano 응답자를 반드시 분리 집계한다.** 같은 기능이 계층에 따라 정반대로 분류될 수 있다. 관리자에게 Must-be인 안전 가드레일이 숙련 작업자에게는 Reverse(있으면 불만)로 나온다. **두 계층의 분류가 갈리는 기능이 곧 제품 내 모드 분리 설계의 근거**다.

**Reverse 항목을 설문에서 열어둔다.** 통제·확인·검증을 강제하는 기능은 숙련 사용자에게 간섭으로 느껴진다. Reverse가 유의하게 나오면 "숙련자 모드 스킵" 같은 설계가 필요하다.

**Must-be는 가중치가 아니라 합격기준이다.** 미충족 시 도입 자체가 무산되는 기능들을 명시적으로 나열한다.

## Phase 5 — 리스크

기능 트리에서 자동으로 나오지 않는, **채택한 설계 때문에 새로 생긴** 리스크를 쓴다. 일반적인 프로젝트 리스크(일정 지연, 인력 부족)는 여기 쓰지 않는다.

각 행은 4열: 리스크 / 내용 / **완화 기능·설계(기능 ID로 연결)** / 잔여 리스크. 완화 수단이 기능 ID로 연결되지 않으면 그 리스크는 대응되지 않은 것이다. **잔여 리스크 열을 비워두지 않는다** — 완전히 해소되는 리스크는 거의 없고, 남는 것을 적는 것이 정직하다.

### 오류비용의 비대칭을 찾는다

판단하는 기능(분기점)이 있으면 **틀리는 두 방향의 대가가 같은지** 확인한다. 다르면 그 사실을 명시하고 안전한 쪽으로 편향된 초기 설정을 설계한다.

> L3(전문가 필요)를 L1(자율)로 오분류 → 감당 못할 조치 시도 → 사고
> L1을 L3로 과분류 → 전문가 호출이 안 줄어듦 → 예전과 동일
> 두 오류의 대가가 다르므로 초기에는 안전측 편향으로 시작해 실적으로 완화한다.

**비대칭 오류비용은 Kano·QFD로 다룰 수 없다.** 별도 FMEA가 필요하다는 것을 다음 단계에 적는다.

## Phase 6 — 대시보드 생성

1. `assets/template.html`을 작업 디렉터리로 복사한다
2. 상단 `DATA` 블록을 채운다 (`references/data-contract.md` 참조)
3. `python scripts/validate.py <파일>` 실행 — 계층 정합성, 기능 기술 형식, 렌더링 오류를 잡는다
4. 검증 통과 후 사용자에게 전달한다

`ENGINE` 영역은 수정하지 않는다. 차트를 바꾸고 싶으면 데이터 형태를 바꾸는 것으로 해결되는지 먼저 본다.

### 문체

분석 문서지 마케팅 자료가 아니다. 각 절의 도입부(`lead`)는 **그 절에서 무엇을 판단해야 하는지**를 쓴다. "본 장에서는 ~을 설명한다" 같은 문장은 아무 정보가 없다.

가장 중요한 판단은 눈에 띄게 놓는다 — 리스크 callout, 포트폴리오 해설, KPI 주의문. **읽는 사람이 이 문서를 덮고 나서 기억해야 할 문장이 무엇인지** 정하고 그것을 강조한다.

## 완료 전 자기점검

- [ ] 기본기능이 경쟁자·수단·"그래서?" 테스트 세 개를 통과하는가
- [ ] 모든 기능이 동사+명사 종결형인가 (모듈명이 하나도 없는가)
- [ ] How-Why가 양방향으로 성립하는가 — `LOGIC` 표에 기록했는가
- [ ] 흐름도에서 분기점과 복귀점을 식별했는가
- [ ] 정량값이 가설임을 명시했는가 / KPI 베이스라인을 `null`로 두고 실측을 다음 단계에 넣었는가
- [ ] 포트폴리오를 **읽고** 해설을 썼는가 (분포 서술이 아니라 판단)
- [ ] VOC가 고객의 날것의 말인가 (번역된 요구사항이 아닌가)
- [ ] 사용자 계층이 둘 이상이면 Kano 분리 집계를 지시했는가
- [ ] 각 리스크의 완화 수단이 기능 ID로 연결되고 잔여 리스크가 적혀 있는가
- [ ] `scripts/validate.py`가 통과하는가
